# Agent Identity & Customer Context Token Specification

This spec covers how the AI agents prove **who they are**, which is the actor (workload) identity, and how the **customer they act for**, the subject identity, travels to the database without being trusted from headers. It implements the target design in the TDD (§4.1 Authentication & Authorization Matrix) and the zero-trust review feedback from 2026-10-29: carry both actor and subject identity on every hop, verify both at each receiver, use short-lived just-in-time credentials, and grant least privilege.

Related specs: [customer-identity.md](customer-identity.md) (REQ-IDENT-*: ingress token verification and `(issuer, subject) → customer_id`), [agent-service.md](agent-service.md) (REQ-AGENT-010 BOLA/IDOR), [ticket-store.md](ticket-store.md) (RLS).

## 1. Requirements

### REQ-AUTH-001: Least-Privilege Custom Inference Roles (replace `roles/aiplatform.user`)
- **Statement**: AI agent identities MUST NOT hold `roles/aiplatform.user`. That role has ~459 permissions, including `reasoningEngines.delete`, `endpoints.deploy` and governance-policy writes. Terraform (`modules/agents-iam`) MUST define project-level custom roles with exactly enumerated permissions, derived from the API calls each agent makes:
  1. `ticketRouterAgentInference` (FaqResolver, `sa-faq`): `aiplatform.endpoints.predict` (Gemini `generateContent` on publisher models).
  2. `ticketRouterTriageRuntime` (TriageRouter, `sa-triage`, and its agent identity under REQ-AUTH-004): `aiplatform.endpoints.predict`, plus the Agent Engine session permissions used by `AdkApp` / `VertexAiSessionService`: `aiplatform.sessions.create`, `aiplatform.sessions.get`, `aiplatform.sessions.list`, `aiplatform.sessions.update`, `aiplatform.sessions.delete`, `aiplatform.sessions.run`, `aiplatform.sessionEvents.append`, `aiplatform.sessionEvents.list`.
  
  The `google_project_iam_member` bindings of `roles/aiplatform.user` to `sa-triage` and `sa-faq` MUST be removed and replaced with bindings to these custom roles. The endpoint-scoped `roles/aiplatform.predictionUser` bindings on router-s1 remain unchanged. When Memory Bank is built, its `aiplatform.memories.*` permissions MUST be added to the custom role explicitly, never by re-granting `aiplatform.user`.
- **Rationale**: An agent holding `aiplatform.user` could delete other agents or rewrite the policies that constrain it (FDE security guidance; TDD §4).
- **Acceptance**: `tests/infra/test_agent_custom_roles_static.py::test_agents_use_enumerated_custom_roles` and `manual: CD smoke after apply (cloud_run_smoke 9/9, identity e2e 5/5, Model Armor 5/5) passes with the custom roles`
- **Status**: done
- **Owner**: identity

### REQ-AUTH-002: Signed Customer Context Token (minting at TriageRouter)
- **Statement**: When, and only when, a turn is handed to FaqResolver for a **verified** customer (`customer_verified = True`, `customer_id` not `anon:`/empty), TriageRouter MUST mint a **customer context token (CCT)**: a compact JWS (ES256) with header `{"alg":"ES256","typ":"JWT","kid":<full KMS cryptoKeyVersion name>}` and claims `iss` (configured minter ID, `CCT_ISSUER`), `sub` (= verified `customer_id`), `aud` (= `CCT_AUDIENCE`, default `order-lookup-mcp`), `iat`, `exp` (= `iat + CCT_TTL_S`, default 300 s, max 600 s), `jti` (random UUID4), `act` (`{"sub": "triage-router"}`) and `tid` (ticket ID). The signature MUST come from Cloud KMS `asymmetricSign` (key purpose `ASYMMETRIC_SIGN`, algorithm `EC_SIGN_P256_SHA256`), with the DER signature converted to raw `r||s` for JWS. No private key material ever exists in application memory or config. Anonymous or unverified turns MUST NOT carry a CCT. Minting failures MUST fail safe: no CCT, the turn continues, and order lookup is then denied downstream. The token, claims and `customer_id` MUST NOT be logged (REQ-AGENT PII rule; log `jti` and `tid` only).
- **Rationale**: Today downstream hops trust `customer_id` because of who the caller is, not because of a signature. A compromised FaqResolver could assert any customer (TDD §4.1 gap).
- **Acceptance**: `tests/identity/test_customer_context_token.py::test_mint_only_for_verified_customers` and `tests/identity/test_customer_context_token.py::test_token_format_and_claims`
- **Status**: done
- **Owner**: identity

### REQ-AUTH-003: CCT Transport and Verification at order-lookup-mcp (RLS from verified claims)
- **Statement**: The CCT MUST travel unchanged from TriageRouter to order-lookup-mcp and be verified there before any data access, as follows:
  1. **Transport**: TriageRouter puts the CCT in the A2A payload field `customer_context_token`. FaqResolver MUST forward it **unchanged** (byte-identical) to `order-lookup-mcp` in the HTTP header `X-Customer-Context`. FaqResolver MUST NOT decode, re-sign or modify it.
  2. **Verification**: `order-lookup-mcp` MUST verify the CCT before any repository call: ES256 signature against the KMS public key for `kid` (fetched with `getPublicKey`, cached ≤ 1 h, `kid` MUST start with the configured `CCT_KEY_PREFIX`), `aud == CCT_AUDIENCE`, `iss ∈ CCT_ALLOWED_ISSUERS`, `exp > now − 60 s`, `iat ≤ now + 60 s`, `exp − iat ≤ 600`, and `sub` non-empty and not `anon:`. The verified `sub` becomes the `customer_id` passed to the repository, which sets `app.customer_id` for RLS (REQ-STORE RLS policy `order_customer_isolation`). Any failure → HTTP 403 `invalid_customer_context`. If a legacy `X-Customer-ID` header is also present and differs from `sub` → 403 `customer_context_mismatch`. A `customer_id` in the request body remains a 400 (REQ-AGENT-010).
  3. **Rollout mode** (production set to `require` on 2026-10-30 after live e2e 5/5 in both `accept` and `require`): `CCT_MODE ∈ {off, accept, require}` (config/env, default `accept`). In `off`, legacy header behavior applies. In `accept`, a present CCT is verified (failure → 403), and when absent the legacy header path applies. In `require`, a CCT is mandatory and the headers alone are rejected (403). Production moves to `require` once the deployed e2e identity check passes in `accept`.
- **Rationale**: Makes RLS rest on a cryptographic customer claim minted at ingress, not on caller trust. Short-lived (5 min) and audience-scoped, so a leaked token is useless elsewhere.
- **Acceptance**: `tests/mcp/test_order_lookup_customer_context.py::test_cct_verification_matrix` and `tests/agents/test_faq_forwards_cct_unchanged.py::test_forward_unchanged`
- **Status**: done
- **Owner**: identity

### REQ-AUTH-004: SPIFFE Agent Identity for TriageRouter (Agent Runtime)
- **Statement**: TriageRouter MUST run under its Agent Runtime **agent identity**, a SPIFFE-based IAM principal `principal://agents.global.org-<ORG>.system.id.goog/resources/aiplatform/projects/<PROJECT_NUMBER>/locations/<REGION>/reasoningEngines/<ID>` with certificate-bound, auto-rotated credentials, instead of the `sa-triage` service account. All grants listed under REQ-AUTH-001/002 for `sa-triage` (custom triage role, router-s1 `predictionUser`, Pub/Sub publisher, `run.invoker` on Cloud Run MCP services, KMS signer, Model Armor user, Cloud Trace agent, Discovery Engine where used) MUST be granted to the agent principal in Terraform. Any remaining need for a Google-signed OIDC ID token (Cloud Run invoker, FaqResolver A2A) MUST be met without long-lived keys, and the mechanism MUST be documented here. The pilot runs on a staging engine first; the production engine switches only after the CD smoke suite passes on staging.
  - **Mechanism (v1)**:
    - **Deploy:** `scripts/deploy_agents/deploy_triage_agent_runtime.py --identity-type agent` deploys through the `vertexai.Client().agent_engines` API with `config.identity_type = AGENT_IDENTITY`, then prints `effective_identity`. The default `--identity-type sa` keeps today's behavior.
    - **Terraform grants:** root variable `triage_agent_principal` (default `""`, meaning no grants). When set, it receives the same project and resource grants as `sa-triage`, plus `roles/iam.serviceAccountOpenIdTokenCreator` on `sa-triage`.
    - **Google-signed ID tokens:** at runtime, setting env `ID_TOKEN_IMPERSONATE_SA=<sa-triage email>` makes `ticket_router.common.idtoken.get_id_token` mint ID tokens with IAM Credentials `generateIdToken` on that SA, using the agent identity's ADC access token. No keys are involved. Receivers (Cloud Run IAM, FaqResolver `ALLOWED_CALLERS`) keep seeing `sa-triage` as the ID-token subject, while every Google API call (Gemini, sessions, router-s1, Model Armor, Pub/Sub, KMS sign) is attributed to the agent principal.
- **Rationale**: Per-agent SPIFFE identity, with no shared SA and no keys, gives precise audit attribution (FDE security guidance; review feedback 2026-10-29).
- **Acceptance**: `manual: staging engine deployed with identity_type=AGENT_IDENTITY; cloud_run_smoke + identity e2e + Model Armor smoke pass against it` (2026-10-30: engine `reasoningEngines/2170218524805431296` promoted to production; GE App agent `11280911196073273342` re-registered to it; CD deploys it with `--identity-type agent`)
- **Status**: done
- **Owner**: identity

### REQ-AUTH-006: mTLS-Aware Google API Transports (certificate-bound agent identity tokens)
- **Statement**: Every Google API call made by the agent code MUST work with **certificate-bound** access tokens. Under agent identity, `google-auth` requests tokens bound to the SPIFFE workload certificate (RFC 8705), and those tokens are rejected with 401 over plain TLS. The calls MUST also keep working unchanged on service-account runtimes (Cloud Run, GKE, the SA-based Agent Engine), where no workload certificate exists. Specifically:
  1. A shared helper `ticket_router.common.google_http` MUST provide `create_google_session(scopes=None, pool_connections=10, pool_maxsize=20) -> (AuthorizedSession, is_mtls: bool)`. It calls `AuthorizedSession.configure_mtls_channel()`, which is a no-op without a workload certificate. The helper MUST also provide `to_mtls_url(url, is_mtls) -> str`, which rewrites `*.googleapis.com` hosts to their mTLS variants when `is_mtls`: `x.googleapis.com → x.mtls.googleapis.com`, `{region}-aiplatform.googleapis.com → {region}-aiplatform.mtls.googleapis.com`, `{svc}.{region}.rep.googleapis.com → {svc}.{region}.rep.mtls.googleapis.com`. All other hosts are left unchanged.
  2. These clients MUST use the helper when no session or token provider is injected: the Model Armor REST client, the KMS signer and public-key resolver, the IAM Credentials `generateIdToken` path, and the router-s1 `rawPredict` client. Injected sessions and token providers keep working, so hermetic tests stay hermetic.
  3. Metadata-server ID tokens for calls to Cloud Run and the A2A peer MUST be **unbound** (`bind_id_token=False` where supported), because those receivers are called on plain `*.a.run.app` and FaqResolver URLs.
  4. The Cloud Trace exporter MUST be built from a `TraceServiceClient` that resolves the mTLS endpoint and client-certificate source (`cloudtrace.mtls.googleapis.com` when a certificate is present). It MUST NOT use `CloudTraceSpanExporter`'s default client, which hard-codes the plain endpoint.
  5. Hosts with no mTLS variant: the router-s1 dedicated endpoint `*.prediction.vertexai.goog` rejects certificate-bound tokens with HTTP 401, even when the client presents the workload certificate (staging pilot 2026-10-30 01:44). It is the ONE stated exception. When the process holds a workload certificate (`is_mtls`), the router-s1 client MUST send an **unbound** access token, fetched with a metadata-server `GET .../service-accounts/default/token` without `certificate_chain` and cached until `expiry − 60 s`, over a plain pooled session. Only `https://` hosts ending in `.prediction.vertexai.goog` may receive it. Any other non-googleapis host keeps the mTLS session. **Accepted risk:** an unbound cloud-platform token can be replayed against any Google API the agent principal can reach until it expires (≤ 1 h), including the KMS signer. Exposure is limited by allowlisting a single https host suffix, never logging the token, and keeping it only in memory. It is recorded in Open Question 3. Without a workload certificate, behavior is unchanged. Each Google API session's auth-refresh retries MUST be configurable, and router-s1 MUST make at most one POST per call (`max_refresh_attempts=0`) so its 0.5 s budget holds.
  6. Session creation failures (ADC or mTLS channel errors) MUST happen inside each client's existing error and circuit-breaker path and degrade safely (Model Armor → DEGRADE verdict, router-s1 → breaker). They MUST NOT raise into the ticket flow, and a failed session MUST NOT be cached.
- **Rationale**: Agent identity tokens are certificate-bound by a Google-managed Context-Aware Access policy. Raw `requests` + Bearer calls fail with 401 (staging pilot 2026-10-30, Open Question 3).
- **Acceptance**: `tests/common/test_google_http.py::test_mtls_session_and_url_rewrite` and `manual: staging agent-identity engine passes scripts/e2e_identity_check.py 5/5`
- **Status**: done
- **Owner**: identity

### REQ-AUTH-007: Agent Gateway Egress Governance for TriageRouter (A2A and Google APIs)
- **Statement**: All outbound traffic from the TriageRouter Agent Runtime engine MUST pass through a Google-managed Agent Gateway `tr-egress` (`networkservices.googleapis.com/agentGateways`, `governedAccessPath = AGENT_TO_ANYWHERE`, us-central1), codified in a separate Terraform root `deploy/terraform/agent-gateway/` on the `google`/`google-beta` 7.x providers (own GCS state prefix `terraform/state/agent-gateway/`; the main root stays on 6.50). The root MUST define: (1) Agent Registry entries (`google_agent_registry_service`) for the FaqResolver A2A agent (agent card served at `/.well-known/agent-card.json`, interface URL = the FaqResolver HTTPS host, exact host match) and a composite `core-gapi` endpoint listing every Google API host TriageRouter calls (standard and mTLS variants): aiplatform, us-central1-aiplatform, aiplatform.us-central1.rep, modelarmor.us-central1.rep(.mtls), cloudkms(.mtls), pubsub(.mtls), iamcredentials(.mtls), cloudtrace(.mtls), telemetry(.mtls), logging(.mtls), monitoring(.mtls), cloudresourcemanager(.mtls), secretmanager(.mtls), agentregistry, the router-s1 dedicated endpoint host (`*.prediction.vertexai.goog`, exact hostname), and the ticket-db-mcp Cloud Run host; (2) an IAP authz extension (`service = iap.googleapis.com`, `iapPolicyVersion = V2`, `failOpen = false`) and a `REQUEST_AUTHZ` / `CUSTOM` authz policy targeting the gateway, with `iamEnforcementMode` controlled by variable `enforcement_mode` (`DRY_RUN` default, `ENFORCE` after logs are clean); (3) an IAM v3 Unified Access Policy + project binding allowing ONLY the TriageRouter agent principal `iap.googleapis.com/resources.egressViaIAP` to the FaqResolver agent and the `core-gapi` endpoint. The engine is bound through the deploy script (`deploy_triage_agent_runtime.py --agent-gateway <name>` → `config.agent_gateway_config.agent_to_anywhere_config.agent_gateway`), re-passing the full env var list including `GOOGLE_API_PREVENT_AGENT_TOKEN_SHARING_FOR_GCP_SERVICES=False`. Hop 1 (customer → TriageRouter) stays on Gemini Enterprise / Agent Runtime IAM with in-agent customer token verification (REQ-IDENT-*), because client-to-agent gateways are not supported for Gemini Enterprise apps.
- **Rationale**: TDD §2.2/§4.1 managed governance at one enforcement point; Agent Gateway (Preview) governs Agent Runtime egress only.
- **Acceptance**: `tests/infra/test_agent_gateway_static.py::test_gateway_root_defines_registry_authz_and_uap` and `manual: gateway logs show TriageRouter → FaqResolver and Google API calls ALLOWED with zero 498/403 in DRY_RUN, then live e2e 5/5 with enforcement_mode=ENFORCE`
- **Status**: done
- **Owner**: identity

### REQ-AUTH-009: order-lookup-mcp Authorizes FaqResolver's SPIFFE Principal (+ customer delegation)
- **Statement**: order-lookup-mcp MUST grant `roles/run.invoker` only to the FaqResolver agent principal (and the CD smoke identity). FaqResolver MUST call it with an **unbound agent-identity ID token** (`fetch_id_token(..., bind_id_token=False)`, audience = the run.app URL). Cloud Run validates the token; the server MUST additionally authorize the caller by decoding the forwarded token payload and requiring `sub` to equal the configured FaqResolver SPIFFE ID (env `ALLOWED_CALLER_SPIFFE_IDS`, comma-separated), returning 403 otherwise, BEFORE CCT verification (REQ-AUTH-003, which stays the customer-delegation check). If agent-identity ID tokens are rejected by Cloud Run, the documented fallback is impersonating a dedicated invoker SA (`roles/iam.serviceAccountTokenCreator` for the agent principal) and authorizing that SA's email instead; the fallback must be recorded here if used.
- **Rationale**: TDD §4.1 hop 3; documented agent→MCP pattern for Cloud Run (IAP with agent-identity callers is undocumented).
- **Acceptance**: `tests/mcp/test_order_lookup_caller_identity.py::test_requires_faq_spiffe_sub_before_cct` and `manual: live e2e own-order lookup succeeds and a request with another principal's token gets 403`

## 2. Open Questions / Deltas

1. **KMS key ring permanence**: Cloud KMS key rings and keys cannot be deleted, only key versions destroyed. The key ring `ticket-router-identity` is therefore permanent in the project.
2. **Agent identity and ID tokens**: whether an Agent Runtime agent identity can mint audience-scoped Google ID tokens directly is unverified as of 2026-10-29. REQ-AUTH-004 resolves it in the staging pilot and records the result here.
3. **Staging pilot result (2026-10-30)**: staging engine `reasoningEngines/2170218524805431296` was deployed with `identity_type=AGENT_IDENTITY`, principal `principal://agents.global.org-349636765856.system.id.goog/resources/aiplatform/projects/620485621180/locations/us-central1/reasoningEngines/2170218524805431296`, and all grants were applied through tfvar `triage_agent_principal`. Live e2e passed 3/5. Gemini (google-genai), the sessions, Tier 2 routing and the BOLA guard work. The custom REST clients that send the agent's access token as a plain Bearer header over non-mTLS endpoints fail with **HTTP 401**: Model Armor (regional `rep` endpoint, so the ticket fails closed to a human), and the Cloud Trace gRPC exporter. Root cause: agent identity access tokens are **certificate-bound** (Context-Aware Access enforces mTLS), so every Google API call must use an mTLS-capable transport (`google.auth.transport.requests.AuthorizedSession.configure_mtls_channel()` with `GOOGLE_API_USE_CLIENT_CERTIFICATE=true`, against `*.mtls.googleapis.com` endpoints). Required before the production switch: move the Model Armor client, KMS signer/resolver, `idtoken` generateIdToken, router-s1 client and the Cloud Trace exporter onto mTLS-aware transports. The production engine stays on `sa-triage` until then. **Follow-up (01:44–02:00):** with the mTLS transports, Model Armor, KMS, IAM Credentials and Cloud Trace all work under agent identity. The router-s1 dedicated endpoint (`*.prediction.vertexai.goog`) still rejects certificate-bound tokens even over mTLS, so router-s1 alone uses an unbound metadata-server token for that host. This is the accepted risk described in REQ-AUTH-006 item 5. Removing it requires either a dedicated endpoint that accepts bound tokens or migrating router-s1 to an mTLS-capable endpoint type.
