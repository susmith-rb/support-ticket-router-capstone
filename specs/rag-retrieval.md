# Specification: RAG Retrieval (`rag-retrieval`)

This specification governs the search configuration, query pre-processing, multi-tier evaluation methodology, citation verification, and regression gating for Google Cloud Agent Search (Discovery Engine).

---

## 1. Overview & Retrieval Pipeline

The retrieval pipeline powers factual resolution in `FaqResolverAgent` by querying the `faq-articles` data store within the `support-kb-search` application.

```
Inbound Customer Message
         │
         ▼
[Query Cleaning (REQ-RAG-RETR-001)] ──▶ Strips @mentions, [TOKENS], hashtags
         │
         ▼
[Agent Search Execution]             ──▶ relevanceThreshold: LOWEST (REQ-RAG-RETR-008)
         │                                Target dataStore: faq-articles
         ▼
[Top-k Retrieved Chunks]             ──▶ Passed to Gemini 3.8 Flash
         │
         ▼
[Answer & Citation Validation]       ──▶ Verbatim quote verification (REQ-RAG-RETR-005)
```

### Evaluation Methodology & Slices

Evaluation is stratified across three tiers to balance realism, benchmarking, and groundedness:

1. **Tier 1: Real-Tweet Retrieval (Hardest, Most Realistic)**:
   - 300 held-out customer tweets from the Kaggle dataset (rag/EVAL_RESULTS.md line 22).
   - Silver ground-truth labels based on the theme from which the answering article was synthesized.
   - Queries are evaluated across three analytical slices:
     - **Slice (a) - All Queries (n=300)**: Unfiltered set including unanswerable or dropped themes.
     - **Slice (b) - Gate Set (n=287)**: Excludes 13 queries matching the 4 dropped praise and social chatter themes (rag/EVAL_RESULTS.md line 180).
     - **Slice (c) - Clean Set (n=242)**: Excludes dropped themes and all queries whose gold targets were merged in v2 (rag/EVAL_RESULTS.md line 183).
2. **Tier 2: Clean-Question Retrieval (Standard Benchmark)**:
   - 106 clean customer questions generated by Claude Sonnet 5.5, 2 per article (rag/EVAL_RESULTS.md line 37).
   - Gold answer is the exact source article used during generation.
3. **Tier 3: Answer Groundedness & Faithfulness**:
   - Answers synthesized by Gemini 3.8 Flash using the top-5 retrieved articles.
   - 100% deterministic verbatim citation precision check across 338 citations (rag/EVAL_RESULTS.md line 186).
   - Atomic-claim support judged by Claude Opus 5.5: 97.7% claim support rate (rag/EVAL_RESULTS.md line 79).
   - Vertex Gen AI Evaluation Service pointwise rubric verification: mean 4.98 / 5.0 (rag/EVAL_RESULTS.md line 94).

## 3. Detailed Requirements

### REQ-RAG-RETR-001: Query Cleaning for Agent Search
- **Statement**: Customer inquiry text MUST be cleaned by removing handle mentions (`@...`), redaction tokens (`[ORDER]`, `[EMAIL]`, `[CARD]`, etc.), and hashtag symbols prior to issuing Agent Search queries.
- **Rationale**: Removes noisy tokens that dilute embedding representations and trigger zero-result searches (TDD §6.3; rag/EVAL_RESULTS.md §2).
- **Acceptance**: `tests/rag/test_retrieval_eval.py::test_clean_strips_mentions_and_tokens`
- **Status**: done
- **Owner**: rag-retrieval

### REQ-RAG-RETR-002: Offline Retrieval Metrics Computation
- **Statement**: The evaluation suite MUST compute exact rank, top-k recall (`recall@1`, `recall@3`, `recall@5`, `recall@10`), and Mean Reciprocal Rank (`MRR@10`) over multi-target evaluation datasets.
- **Rationale**: Standardized retrieval evaluation against established TDD benchmarks (TDD §6.4).
- **Acceptance**: `tests/rag/test_retrieval_eval.py::test_compute_recall_at_k`
- **Status**: done
- **Owner**: rag-retrieval

### REQ-RAG-RETR-003: Gold Map Resolution in Retrieval Evaluation
- **Statement**: The evaluation harness MUST accept `--gold-map` to resolve historical ground-truth document IDs to merged, split, or renamed successor IDs in new corpus releases.
- **Rationale**: Enables automated before-and-after evaluation parity across corpus revisions without re-annotating historical queries (TDD §6.4, §6.6).
- **Acceptance**: `tests/rag/test_retrieval_eval.py::test_gold_map_mapping`
- **Status**: done
- **Owner**: rag-retrieval

### REQ-RAG-RETR-004: Regional and Multi-Region Search Endpoint Resolution
- **Statement**: Search utilities MUST support `--location` (`global` or `us`) and dynamically resolve Discovery Engine API hosts (`discoveryengine.googleapis.com` vs `us-discoveryengine.googleapis.com`) and serving config resource paths. The default location MUST remain `global` unless a migration parity gate is satisfied: `us Δrecall@5 ≥ −0.02` overall on slice (b) (n=287).
- **Rationale**: Permits evaluating and serving search requests against both global and regional data stores (TDD §4.1; PLAN2.md §Workstream L). Switching the default serving location requires verifying that regional index quality matches or exceeds global within acceptable ranker tolerance without introducing silent deflection regressions.
- **Acceptance**: `tests/rag/test_retrieval_eval.py::test_retrieval_eval_location_us`
- **Status**: done
- **Owner**: rag-retrieval
- **Migration Decision Rule & Evidence (2026-10-24)**:
  - **Decision Rule**: Flip `--location` default to `"us"` IF AND ONLY IF `us Δrecall@5 ≥ −0.02` overall on slice (b) (excluding dropped themes, n=287).
  - **Parity Results**:
    - Global run 1 baseline: `recall@1=0.411`, `recall@3=0.690`, `recall@5=0.780`, `recall@10=0.875`, `MRR@10=0.567`.
    - Global run 2 repeat: `recall@1=0.411`, `recall@3=0.690`, `recall@5=0.780`, `recall@10=0.875`, `MRR@10=0.567` (0.000 stochastic noise across all metrics).
    - US run 2 (post-settlement >3h): `recall@1=0.369`, `recall@3=0.627`, `recall@5=0.753`, `recall@10=0.829`, `MRR@10=0.521`.
    - Delta (`US - Global`): `Δrecall@5 = −0.027` (failed gate `≥ −0.020`).
    - Paired analysis (Top-5): 205 both hit (71.4%), 19 global-only hit (6.6%), 11 us-only hit (3.8%), 52 neither hit (18.1%). Net change: −8 hits.
    - Intent family breakdown: `order_status` Δ = −0.113 (0.845 vs 0.732), `account_payment` Δ = −0.087 (0.804 vs 0.717), `returns_refunds` Δ = −0.023 (0.818 vs 0.795), `other` Δ = +0.068 (0.658 vs 0.726), `shipping_policy` Δ = +0.111 (0.778 vs 0.889).
  - **Outcome**: Migration gate FAILED (`−0.027 < −0.020`). Decision is final: Agent Search serves permanently from `global`, per the user, 2026-10-24. Existing `global` resources are brought under Terraform management; unmanaged `us` data stores and search engines are decommissioned. Regional infrastructure remains in `us-central1`. Explicit `--location us` remains supported for regional workflows.

### REQ-RAG-RETR-008: Agent Search Relevance Threshold Configuration
- **Statement**: All Agent Search queries MUST pass `relevanceThreshold: LOWEST` to prevent the search engine from silently discarding noisy or colloquial customer queries.
- **Rationale**: The default threshold dropped 113 of 300 real customer queries (38%) with zero results; LOWEST recovered 104 queries and raised recall@5 from 0.467 to 0.750 (TDD §6.3; rag/EVAL_RESULTS.md §2).
- **Acceptance**: `manual: python rag/retrieval_eval.py --threshold LOWEST --clean`
- **Status**: done
- **Owner**: rag-retrieval

### REQ-RAG-RETR-009: Query-Time Status and Effective-Window Filtering
- **Statement**: Search queries SHOULD pass filter expressions ensuring `status = "active"` and `effective_from <= CURRENT_TIMESTAMP AND effective_to >= CURRENT_TIMESTAMP` once human reviews are completed. Until human SME review promotes corpus articles to `active`, clients MUST default to `allowed_statuses = ["active", "draft"]` (`status: ANY("active", "draft")`).
- **Rationale**: Enforces lifecycle governance ensuring draft or decommissioned articles are excluded from customer answers while preserving full recall during pre-publication stages (TDD §6.3, §6.6).
- **Acceptance**: `tests/rag/test_search_client.py::test_search_client_status_filter_applied`
- **Status**: done
- **Owner**: rag-retrieval
- **Live Probe Verification (2026-10-24, Discovery Engine `global`)**:
  - **Probe 1 (`allowed=['active']`)**: Returns 0 results (`totalSize=0`), confirming that Discovery Engine strictly enforces the filter and that no draft articles leak when restricted to `active`.
  - **Probe 2 (`allowed=['active', 'draft']` vs unfiltered)**: Evaluated across 20 held-out test queries; 20/20 (100%) produced identical retrieved document IDs in identical order, proving zero query loss and complete operational parity.
  - **Probe 3 & 4 (Intent & Datetime Filter Syntax)**: Confirmed that string property filtering uses `field: ANY("val1", "val2")` and datetime comparisons use `effective_from <= "<ISO_TIMESTAMP>"`. Combined clauses (`status: ANY("active", "draft") AND intent_family: ANY(...)`) execute hermetically.

### REQ-RAG-RETR-010: Intent Family Query Boost and Fallback
- **Statement**: The search client SHOULD apply intent-based document boosting aligned with the router's predicted intent family via `boostSpec.conditionBoostSpecs`, parameterized dynamically via runtime configuration (e.g. `intent_boost: float = 0.2`, rather than hardcoded in source), automatically falling back to an unconstrained search if hard filtering is used and fewer than `fallback_min_results` candidates are found.
- **Rationale**: Soft boosting narrows candidate retrieval spaces and prioritizes the predicted intent family without brittle candidate truncation or sensitivity to missing metadata attributes (TDD §6.3).
- **Acceptance**: `tests/rag/test_search_client.py::test_search_client_soft_boost_condition`
- **Status**: done
- **Owner**: rag-retrieval
- **Evaluation Evidence on TEST and DEV Sets (2026-10-24)**:
  - **Hard Filter vs. Soft Boost Comparison**:
    - *Hard Filter (Oracle vs Noisy)*: With hard filtering (`intent_family: ANY(...)`), any upstream router error causes severe query loss. On DEV post-metadata fix, 14% router error collapsed recall@5 from 0.8958 (oracle) down to **0.7500** (−3.12% below baseline 0.7812).
    - *Soft Boost Resilience*: Soft boost applies an additive score boost (`boostSpec.conditionBoostSpecs`) to matching documents while leaving non-matching documents eligible for semantic/lexical match. With 14% router noise on DEV, soft boost 0.2 achieved `recall@5=0.8403` (+5.91% over baseline), and on the frozen TEST set achieved `recall@5=0.8223` (+4.18% over baseline 0.7805), with zero empty fallbacks triggered.
  - **Live Fallback Probe Verification**: Probe 4 confirmed that cross-intent queries with default threshold returning < 2 results automatically trigger unconstrained fallback, returning valid cross-family articles (`fallback_triggered = True`).

## 4. Open Questions / Deltas

1. **Target vs. Measured Quality Gap**:
   - `recall@5`: Target is `≥ 0.90` (TDD §6.4 Gate G5). Measured on real tweets is `0.780` (v2 release 3) / `0.760` (v1) on the gate set; clean questions achieve `0.840` (v1) / `0.821` (v2) (rag/EVAL_RESULTS.md lines 180, 184).
   - `MRR`: Target is `≥ 0.75` (TDD §6.4 Gate G5). Measured on real tweets is `0.562`; clean questions achieve `0.650` (v1) / `0.681` (v2) (rag/EVAL_RESULTS.md lines 180, 185).
   - `nDCG@5`: Target is `≥ 0.80` (TDD §6.4 Gate G5); not currently instrumented in offline evaluation scripts.
   - `p95 Latency`: Target is `≤ 400 ms` (TDD §6.4 Gate G5); live load-test benchmarking is pending.
2. **Query Filters Operational Resolution**: Status filtering is implemented in `rag/search_client.py` with `allowed_statuses = ["active", "draft"]` (`status: ANY("active", "draft")`) as the safe operational default. Live probe 1 verified `allowed=['active']` returns 0 results, while probe 2 verified `allowed=['active', 'draft']` achieves 100% parity with unfiltered search across test queries. When human review promotes articles to `active`, the filter seamlessly restricts retrieval without client changes.
3. **Ranker Noise Floor vs. Gate Sensitivity**: The ranker noise floor was measured at `~4.6%` on unchanged intent families (`returns_refunds` fell 0.046 between v1 and v2 despite zero article edits, rag/EVAL_RESULTS.md line 193). With `n=287` queries, the `−0.02` regression gate is close to the stochastic noise floor of the underlying Discovery Engine ranker. Future gates should average over 2–3 query samplings.
4. **Location Parity Gate Result (Global vs. US Multi-Region)**:
   On 2026-10-24, after >3h index settlement, retrieval parity was evaluated across Global and US multi-region on slice (b) (n=287). The Global repeat run showed 0.000 stochastic ranker noise (exact identical ranks and metrics). US recall@5 was 0.753 vs Global 0.780 (Δ = −0.027), failing the Δ ≥ −0.020 migration gate. Notable regressions occurred in `order_status` (−0.113) and `account_payment` (−0.087). Consequently, default location remains `global` in all utilities; explicit `--location us` remains supported.

- **Statement**: Evaluation of retrieval quality MUST maintain strict split discipline between a frozen TEST set (300 queries from release 2b) and a disjoint DEV set (300 queries from non-example held-out threads). - **Rationale**: Prevents overfitting to the test distribution during search parameter tuning and ablation studies (TDD §6.4; PLAN3.md D3, D4).
- **Acceptance**: `tests/rag/test_build_eval_splits.py::test_splits_disjointness`

### REQ-RAG-RETR-015: Multi-Relevant Retrieval Measurement & Adjudication Evaluation
- **Statement**: Retrieval evaluation MUST support multi-relevant ground truth labeled by two independent blind annotators (A, B) and an adjudicator (C) per `docs/plans/PLAN4.md`. Metrics and statistics computed MUST include:
  1. **Inter-Annotator Agreement**: Cohen's $\kappa$ on `support_request` (binary) and `primary` (categorical), exact-match rate on `primary`, and mean Jaccard overlap of relevant sets across common queries.
  2. **Scope Filtering & Exclusion Accounting**: Evaluated on `MAIN` scope (`support_request == True` AND `language == "en"` AND `primary is not None`) and `ALL-support` scope (`support_request == True` AND `primary is not None`), with waterfall accounting of excluded queries by reason (`not_support_request`, `non_english`, `no_primary`).
  3. **TDD §6.4 Consensus Retrieval Quality Metrics**: Adjudicated consensus labels (C) evaluated for `recall@5` (any consensus doc in top 5), `MRR@10` (rank of first consensus doc), and graded `nDCG@5` (gain: primary=2, other relevant=1; IDCG normalized against query's own label set).
